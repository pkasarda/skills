# New project

Start from the first real flow and the user's goal. A learning prototype, an internal tool and a customer service may need different proof and operating constraints. Preserve a chosen platform; choose a minimal provisional structure only when the next step needs it.

1. Extract the actor, job, expected outcome and constraints already supplied. Use product-discovery if available for consequential gaps. Keep a sufficiently specified build request moving.
2. Describe the first complete flow, its main refusal/recovery, relevant access rules and which effects must be durable or indivisible. Make assumptions visible. A screen mock is a learning artifact unless its real effects were implemented and verified.
3. Name logical owners and the smallest plausible seams. Keep unimplemented modules, schemas and deployment choices proposed. Use the relevant design or authorization procedure where those decisions are needed; avoid inventing a framework from the product's name.
4. Prepare only the requested next artifacts: a compact product/spec document, a small instruction router, or a few issue drafts. Reach the artifact guide from the main skill when writing them. A blank repository has no verified test command or existing API; state that gap rather than manufacturing one. Classify unknowns by who can resolve them: routine reversible runtime/library choices can belong to the implementing agent within an authorized build. They are proposed design work, not automatically a maintainer approval or prerequisite ticket. A not-yet-configured test command is an evidence gap, not a product blocker.
5. Select the first observable slice or experiment. Its acceptance should distinguish the central rule and a meaningful failure where relevant. A separate infrastructure slice is valid when it has a real prerequisite contract; screens, database and API need not automatically become separate tickets.

Exit when the next step has a clear purpose, enough accepted behavior, explicit assumptions and a way to observe success or refusal. Name the concrete consequence of any blocking decision. Preserve a usable first slice where a transparent working assumption or bounded refusal can safely contain an unresolved edge; do not label every assumption as blocking all implementation. A blocking product choice holds its dependent implementation, while other requested setup can continue. Documents, live service readiness and implementation completion remain separate results.
