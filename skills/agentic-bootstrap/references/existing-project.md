# Existing project

Begin with the actual working scope and expand only when a relevant owner or pointer crosses it. A new developer or new feature does not make an established system a blank slate.

- Inspect the effective root/scoped instruction chain, current configuration and entrypoints for the affected flow. Follow its actual readers, writers, schema and relevant checks. Keep generated maps and historical proposals as leads.
- Read accepted decisions and relevant issue/PR history when available. Distinguish intended behavior, current source and observed runtime. Current code proves what is implemented; it does not silently replace an accepted future product decision. An open PR or proposal is not delivered behavior.
- Inventory current document owners before adding files. Reuse a glossary, access policy, ADR or feature spec with the right scope. Surface contradictions with concrete consequences and evidence; preserve already decided product choices.
- Map the minimum needed capability and owner, existing gates and gaps. Record a reviewed revision or unversioned-fixture status, coverage and unrun checks. A source-only onboarding does not establish deployed correctness.
- Preserve shared conventions, safety rules, programme pauses, active writers and canonical backlog relationships. Reconcile duplicate/superseded work before proposing another implementation. Existing but imperfect architecture normally needs a bounded repair or documented decision, not an onboarding rewrite.

When producing instructions, use the disclosure guide from the main skill. Put package-only rules at their real scope; keep shared root rules intact. An installed instruction-refactoring procedure can help with a substantive rewrite, but inspect its scope before using it. Bootstrap still works without that additional skill.

Exit with enough accurate context for the requested next task, a narrow correction to confirmed documentation drift, and explicit unresolved decisions. Do not scan unrelated packages merely to fill a universal dossier. A paused feature may receive a useful handoff without becoming available for implementation.
